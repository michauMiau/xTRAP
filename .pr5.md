## Four faults in the firmware, all found on the bench

### 1. No motor failsafe

`T,100` latched forever. A dropped WiFi link or a crashed client left the car at
full throttle with nobody holding the controls.

Now a plain `time.ticks_diff(now, last_drive_time) > FAILSAFE_MS` comparison,
`FAILSAFE_MS = 1000`, refreshed by every `T` command. `stop()` is called on
**every tick** past the threshold, not only on the first — a `T0` may never
arrive. The comparison is against a timestamp, never a sticky boolean, which
would latch true after the first packet and disable the timeout entirely. Logged
when it fires.

### 2 & 3. The servo was out of spec, then had no holding signal

```python
for _ in range(3):
    self.write_pulse(pulse)   # pulse = 1500us at 90 degrees
```

Three 1500μs pulses with no gap is **4500μs of continuous HIGH** — roughly 3x
what a hobby servo accepts (500–2500μs). The car drove into the end stop.

Separately, `_step()` returned early once `angle == target`, so after arriving
the servo received **no pulses at all**. A servo has no holding torque without a
frame, so it sagged the moment it got where it was asked to go.

Both are fixed by handing the 20ms frame to the LEDC peripheral: the channel
keeps emitting 50Hz forever, which gives holding torque at rest, and
`set_angle()` no longer busy-waits, so the receive loop stops losing commands.

### 4. GPIO3 was wired but never driven

Both servos are now built from `PINS` and stepped on the same 20ms tick, so the
mechanically linked pair cannot drift apart.

## Pins are configuration

Every output now lives in one dict at the top:

```python
PINS = {
    "servo_left": 2, "servo_right": 3,
    "motor_in1": 6, "motor_in2": 4,   # MX1508
    "backlight": 38,
}
```

No bare GPIO numbers are left in the driver classes. The dict records that
`I2C(0)` is **GPIO8/9** on this firmware, resolved from `mpconfigboard.h` — the
vendor's stock Cardputer firmware maps the same bus to GPIO1/2, which *would*
collide with `servo_left`.

## Documentation that was actively misleading

- `architecture.md` listed the servo on **"Pin 4"** — that is the motor's reverse
  input. Anyone trusting it would have commanded the motor while believing they
  were steering.
- `README.md` named port **5006** in three places. The firmware binds 5005.
- `README.md` advertised `Acceleration_live_recorder.py`, which is not in the repo.
- `architecture.md` Known Issues still read "Motor controller not working" after
  the motor code had existed for some time.
- The I²C table row now states the resolved pins instead of the bus number.

## Tests

28 new, 72 total. `rcar.py` cannot be imported — it opens WiFi, binds a socket
and runs `while True` at module level — so the harness stubs `machine` and
executes the real `Servo`/`Motor` classes and the real constants **out of the
file** via `ast`. The tests read the shipped source, not a copy of it.

All four regressions were confirmed to fail when reintroduced: the 3-pulse loop
(2 failures), the failsafe removed (2), the second servo aliased (1), and
`servo_right` moved to another pin (3).

**Not verified on hardware.** The Cardputer was not reachable over the network,
so nothing here has run on the bench. Both changes that touch moving parts —
the second servo and the new servo drive path — are the ones to watch on first
power-up with the wheels off the ground.
